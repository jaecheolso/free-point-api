## 과제 설명
무료 포인트 시스템(API) 구현. 개발 환경: Java 21, Spring Boot 3.5.16, H2 2.3.232

### 필요 기능
1. 적립
   1. 1회 적립가능 포인트는 1포인트 이상, 10만포인트 이하로 가능하며 1회 최대 적립가능 포인트는 하드코딩이 아닌 방법으로 제어할 수 있어야 한다.
   2. 개인별로 보유 가능한 무료포인트의 최대금액 제한이 존재하며, 하드코딩이 아닌 별도의 방법으로 변경할 수 있어야 한다.
   3. 특정 시점에 적립된 포인트는 1원단위까지 어떤 주문에서 사용되었는지 추적할 수 있어야 한다.
   4. 포인트 적립은 관리자가 수기로 지급할 수 있으며, 수기지급한 포인트는 다른 적립과 구분되어 식별할 수 있어야 한다.
   5. 모든 포인트는 만료일이 존재하며, 최소 1일 이상 최대 5년 미만의 만료일을 부여할 수 있다. (기본 365일)
2. 적립취소
   1. 특정 적립행위에서 적립한 금액만큼 취소 가능하며, 적립한 금액 중 일부가 사용된 경우라면 적립 취소될 수 없다.
3. 사용
   1. 주문시에만 포인트를 사용할 수 있다고 가정한다.
   2. 포인트 사용시에는 주문번호를 함께 기록하여 어떤 주문에서 얼마의 포인트를 사용했는지 식별할 수 있어야 한다.
   3. 포인트 사용시에는 관리자가 수기 지급한 포인트가 우선 사용되어야 하며, 만료일이 짧게 남은 순서로 사용해야 한다.
4. 사용취소
   1. 사용한 금액 중 전체 또는 일부를 사용취소 할 수 있다.
   2. 사용취소 시점에 이미 만료된 포인트를 사용취소 해야 한다면 그 금액만큼 신규적립 처리한다.

### 예시
1. 1000원 적립한다 (총 잔액 0 -> 1000원) — pointKey : A
2. 500원 적립한다 (총 잔액 1000 -> 1500원) — pointKey : B
3. 주문번호 A1234 에서 1200원 사용한다 (총 잔액 1500 -> 300원) — pointKey : C
   - A 적립에서 1000원 사용 -> A의 사용가능 잔액 1000 -> 0
   - B 적립에서 200원 사용 -> B의 사용가능 잔액 500 -> 300
4. A의 적립이 만료되었다
5. C의 사용금액 1200원 중 1100원을 부분 사용취소 한다 (총 잔액 300 -> 1400원) — pointKey : D
   - A는 이미 만료되었으므로 pointKey E 로 1000원이 신규적립된다.
   - B는 만료되지 않았으므로 사용가능 잔액 300 -> 400원이 된다.
   - C는 이제 1200원 사용금액 중 100원을 부분취소 할 수 있다.

### 설계 참고
- **잔액 모델**: 적립 1건마다 Lot(`point_lot`) 1개를 만들고, 잔액은 Lot에만 둔다. 잔액은 유효한 Lot의 남은 금액 합계이며 따로 캐시하지 않는다.
  - 사용 시 Lot 단위로 차감하고, 어떤 사용 거래가 어떤 Lot에서 얼마를 썼는지 `point_use_detail`에 기록한다. (1-3 "1원 단위 추적")
  - 차감 순서: 수기지급 우선 → 만료일 임박 순 → 적립 순 (3-3)
- **만료**: 만료 배치 없이 `expires_at <= 현재 시각`이면 만료로 판정한다. 만료된 Lot은 잔액, 사용, 보유 한도 계산에서 제외된다.
- **시각**: 요청의 `expiresAt`을 포함한 모든 시각은 KST(Asia/Seoul) 기준이다. 서버 기본 시간대와 무관하도록 `Clock`을 KST로 고정했다.
- **사용취소**: 원 사용 때 차감한 순서대로 되돌린다.
  - 원 Lot이 만료 전이면 그 Lot의 잔액을 복원한다.
  - 원 Lot이 만료됐으면 취소 금액만큼 신규 적립한다(4-2). 재적립은 `EARN` 거래로 기록하고, Lot의 `origin_type = USE_CANCEL_REISSUE`로 일반 적립과 구분한다. 만료일은 기본 만료 기간을 따르고, 수기지급 여부는 원 Lot에서 승계한다.
  - 재적립은 이미 보유했던 포인트를 되돌려주는 것이므로 1회 적립 한도와 보유 한도를 검사하지 않는다.
- **정책**: 전역 정책(`point_policy`)으로 1회 최대 적립액과 최대 보유 한도를 관리한다. 개인별 보유 한도(`point_user_policy`)가 있으면 보유 한도만 전역 정책을 덮어쓴다. (1-1, 1-2)
  - 관리자 API(`/api/admin/policies`)로 변경한다. 기존 행을 `effective_to`로 닫고 새 행을 추가해 변경 이력을 남긴다.
- **동시성**: 잔액이나 한도에 영향을 주는 모든 요청(적립, 적립취소, 사용, 사용취소, 개인 한도 변경)은 `point_account` 행을 `SELECT ... FOR UPDATE`로 잠가 사용자 단위로 직렬화한다.
  - Lot이 아닌 계정 행을 잠그는 이유: 적립은 새 Lot을 INSERT 하므로 잠글 행이 없고, 보유 한도 검사까지 직렬화해야 하기 때문이다.
  - 만료 판정과 정책 적용 기준인 현재 시각은 락을 얻은 뒤에 읽는다. 락을 기다리는 동안 흐른 시간을 반영하지 못하면 이미 만료된 Lot을 유효하다고 판단하거나, 개인 정책이 두 개 열릴 수 있기 때문이다.
  - 트랜잭션 격리 수준은 READ COMMITTED로 고정한다. 취소 요청은 락 전에 pointKey로 사용자를 조회하는데, MySQL 기본값(REPEATABLE READ)에서는 이 조회 시점에 스냅샷이 고정돼 락을 얻은 뒤에도 앞선 요청의 커밋을 보지 못하기 때문이다.
  - 전역 정책을 동시에 변경하면 먼저 커밋된 변경만 반영하고 나머지는 409로 거절한다. 앞선 변경을 보지 못한 채 덮어쓰는 것을 막기 위함이다.
- **멱등성**: 포인트 거래 요청(적립, 적립취소, 사용, 사용취소)은 `requestId`를 받는다(UNIQUE). 같은 요청을 재시도하면 기존 결과를 그대로 돌려주고, 다른 요청에 이미 쓰인 `requestId`면 409로 거절한다.
  - 같은 `requestId`라도 요청 내용(금액, 주문번호, 수기지급 여부, 만료일)이 다르면 409로 거절한다. 만료일은 초 단위로 맞춰 저장·비교하며, 요청에 값이 있을 때만 비교한다. 생략하면 기본 만료 기간을 요청 시각 기준으로 계산하므로, 재시도 시점에 다시 계산한 값과 달라지기 때문이다.
- 테이블 간 물리 FK는 설정하지 않았다. 관계는 논리적으로만 두고(`schema.sql` 각 테이블 주석의 "논리 FK" 참고) 참조 무결성은 애플리케이션에서 보장한다.
  - 운영 환경(Aurora MySQL)에서의 샤딩·온라인 DDL·데이터 이관 유연성을 고려했다.
  - InnoDB는 자식 행 INSERT 시 부모 행에 공유 락을 걸기 때문에, 동시성 제어용으로 잠그는 `point_account` 행에 의도치 않은 락이 추가되는 것을 피했다.
  - 금액 정합성(음수 금지, 초과 취소 금지, 멱등 키)은 CHECK / UNIQUE 제약으로 DB에서 강제한다.

## 빌드 및 실행
요구사항: Java 21

```bash
./gradlew build     # 빌드 + 테스트
./gradlew bootRun   # 실행 (http://localhost:8080)
```
- Swagger UI: http://localhost:8080/swagger-ui.html
- 테스트 계정: `userId` 1~5 (`data.sql`로 생성). 계정 생성 API는 없으며, 운영에서는 회원 가입 시 생성된다고 가정한다.
- H2 콘솔: http://localhost:8080/h2-console (JDBC URL `jdbc:h2:mem:point` / User `sa` / Password 없음)
